# v0.7: a live backend on Google Sheets

**Date:** 18 Nov 2026

Until now the server ran on the studio's laptop: the app worked only while the laptop was on and reachable, which
suits a demo, not a class of ten that meets every morning. The backend is now a Google Apps Script web app bound to
a Google Sheet in the studio's Drive folder. It answers every route the app uses, with the same rules and the same
JSON as the laptop's FastAPI server, and the Sheet is a database the owner can open, read and query.

How it works, the envelope, the tabs, limits and security: [`appsscript/README.md`](../../appsscript/README.md).

## Why a Google Sheet

- **Free, with nothing to run.** Apps Script web apps and Sheets cost nothing on a personal Google account: no
  server, no domain, no card, no laptop left on.
- **Enough for this studio.** About ten students and twenty check-ins a day, against quotas of 30 simultaneous
  requests and ten million cells. Each call takes one to three seconds, which a check-in tap can bear.
- **The data stays readable.** Every table is a tab. A Dashboard tab of `QUERY` formulas shows students by status,
  attendance per class over time, mood before and after per class, feedback and shared notes, and the owner can add
  her own.
- **One place.** The data (the Sheet), the backend (the script bound to it) and the model file for Gemma on the
  phone all sit in the studio's Google Drive.

Considered and set aside: keeping the laptop online through a tunnel (the laptop must stay on), a free cloud server
or function (an account with a card, upkeep, cold starts), and a hosted database such as Firebase (the data is no
longer something the owner can browse and query as a sheet).

The costs of the choice: Apps Script cannot read request headers or set an HTTP status, so the app talks to it
through an envelope; writes take one lock, one at a time; and each call takes about a second before any work starts.

## What was built

| Piece | What it does |
|---|---|
| The envelope | Every call is a POST of `{method, path, query, token, body}`; every answer is HTTP 200 with `{status, body}`, `status` being the HTTP status the answer stands for. A plain GET answers the health check |
| 24 routes | Accounts, the Today screen, check-ins, feedback, the teacher's screens, WhatsApp sharing and invites, and the three routes for Gemma on the phone: `/me/practice`, `/me/shared`, `/teacher/shared`. `/chat`, `/ask` and `/me/notes` are gone: questions never reach the server |
| Storage | One tab per table, columns found by header name, text written so Sheets keeps it as typed, times as date cells in India time, writes under the script lock, ids worked out under it |
| Security | One permission (this spreadsheet only), login tokens stored as SHA-256, passwords salted and stretched with SHA-256, lockouts after 5 failures, a dummy hash for unknown numbers |
| `setup()` | Makes the tabs, the teacher and group codes (in a hidden settings tab), the classes tab and the Dashboard. Safe to run again |
| The paste bundle | [`appsscript/dist/Code.gs`](../../appsscript/dist/Code.gs), built from `appsscript/src/` with the studio content generated from `backend/content/studio.json`. The owner created the Sheet in the folder, pasted the file, ran `setup` and deployed it in a few minutes, with no command-line tools signed in to her Google account |

## How we know it matches

The tests run the same `Code.gs` the owner pastes, in Node, with small fakes of the Google services
(`node --test 'appsscript/test/*.test.mjs'`, 70 tests, about a second). They cover the rules the FastAPI tests
encoded (one teacher, the teacher code in any case, the group code, pending and approved, phone numbers however
typed, check-in windows, lockouts, links cleaned, settings saved both or neither) and what is particular to a
Sheet: text that Sheets would turn into a number or a formula, columns moved by hand, the lock, the cache.

A parity check went further: the same 101 requests went to the FastAPI server and to this backend at the same frozen
moment, and every answer was compared. Two differed:

| Finding | Fix |
|---|---|
| A 422 for a bad path parameter named it `id`; FastAPI names it `session_id` or `user_id` | Path parameters carry FastAPI's names |
| Students (and feedback) signed up in the same second came back in a different order | Equal times keep the order written, as SQLite's sort does |

After the fixes all 101 match. FastAPI's answers are kept as a fixture
([`appsscript/test/parity/`](../../appsscript/test/parity/)), so the check outlives the FastAPI server. A mutation
check broke six rules in the bundle one at a time (rounding, the apostrophe for text, the dummy hash, the login
lockout, the check-in window, a re-check under the lock); the suite caught five. The sixth only matters when two
teachers sign up in the same second, which the fakes cannot stage.

## On the live Sheet

The owner deployed the web app. It was smoke-tested with requests that write no row
([`appsscript/scripts/smoke.mjs`](../../appsscript/scripts/smoke.mjs)): the health check, the studio in three
languages, a bad envelope, an unknown path, a wrong method, signed-out calls, sign-ups refused by validation or a
wrong group code, one wrong teacher code, and failed logins for numbers that cannot be real mobiles. All 18 checks
passed in both runs.

| Request | Median, end to end |
|---|---|
| No Sheet work (health, studio, refusals) | 0.8 to 1.1 s |
| Reading one tab (an unknown token) | 1.9 s |
| A failed login (a tab, the password hash, the lockout) | 2.7 s |
| The first Sheet read after a quiet spell | 2.7 s and 5.4 s |

The password hash and the lockout bookkeeping cost about 0.8 s per login, the difference of the last two medians
over 12 interleaved pairs. A student's Today screen and a check-in were not timed live, so as not to write to the
studio's Sheet; from the parts, expect two to three seconds each.

## Left for later

- The app's HTTP client speaks the envelope (the next task); until then the app still expects the laptop server.
- The laptop's FastAPI server is retired, and the Node tests become the backend's only tests.
- Accounts start fresh on the Sheet: nothing was copied from the laptop's database.
- The lockout counters live in Apps Script's cache, which can evict them early.
